# 아키텍처

## 1. 설계 목표

이 프로젝트는 평소 트래픽은 낮지만 **티켓 오픈 순간에만 수만~수십만 명이 몰리는** 전형적인 스파이크 워크로드를 가정한다. 목표는 세 가지다. 첫째, 트래픽 스파이크에도 서비스가 죽지 않을 것(가용성). 둘째, 좌석/재고가 절대 초과 판매되지 않을 것(정합성). 셋째, 먼저 온 사용자가 먼저 처리될 것(공정성). 이 세 목표가 서로 충돌하는 지점에서 어떤 트레이드오프를 했는지가 이 프로젝트의 핵심 어필 포인트다.

## 3. 전략 ① 가상 대기열 (Waiting Queue)

트래픽이 백엔드를 직접 때리지 못하게 하는 **댐** 역할이다. 사용자가 예매 페이지에 진입하면 곧바로 비즈니스 로직을 타지 않고 대기열에 등록된다.

- **자료구조**: Redis Sorted Set. `score = 진입 타임스탬프(ms)`, `member = userId`. score 순서가 곧 입장 순서가 되어 FIFO 공정성을 보장한다.
- **순번 조회**: `ZRANK`로 내 앞에 몇 명이 있는지 O(log N)에 계산한다. 프론트는 이 값을 폴링하여 "내 순번 / 예상 대기시간"을 보여준다.
- **입장 제어**: 별도 워커가 일정 주기로 `ZPOPMIN`을 통해 "활성 사용자 풀(active set)"이 정원에 찰 때까지 사용자를 꺼내, 짧은 만료의 **입장 토큰(JWT)**을 발급한다. 이 토큰이 있어야 예매 API를 호출할 수 있다.
- **효과**: 백엔드는 항상 "정원만큼"의 사용자만 상대하므로 부하가 일정하게 유지된다.

## 4. 전략 ② 재고 동시성 제어

대기열을 통과해도, 인기 좌석에는 여전히 동시 요청이 몰린다. 여기서 오버셀을 막는 것이 핵심이다.

- **DB 락만으로는 부족**: 행 잠금/비관적 락은 스파이크에서 커넥션 풀을 고갈시키고 데드락 위험이 크다. 그래서 **1차 방어선은 Redis**다.
- **Redis Lua 원자 연산**: 좌석 점유 차감을 Lua 스크립트로 처리한다. "남은 재고 확인 → 0보다 크면 차감 → 점유 키 설정"을 단일 원자 연산으로 실행해 경합 구간(check-then-act race)을 제거한다.
- **좌석 점유 TTL**: 좌석을 고른 사용자에게 N분짜리 임시 점유(hold)를 준다. 결제까지 못 가면 자동 만료되어 재고로 복귀한다.
- **2차 방어선 DB**: 최종 커밋 시 DB의 유니크 제약 + 트랜잭션으로 정합성을 한 번 더 보장한다. Redis는 빠른 게이트, DB는 진실의 원천(source of truth).

## 5. 전략 ③ 비동기 예매/결제 (Kafka)

예매 "요청"과 예매 "확정"을 분리한다.

- **Producer**: 예매 API는 검증만 마치면 `reservation.requested` 토픽에 이벤트를 던지고 즉시 202(Accepted)를 반환한다. 사용자 응답 시간이 결제·DB I/O에 묶이지 않는다.
- **Consumer**: 컨슈머 그룹이 자기 속도대로 이벤트를 소비하며 재고 확정 → 결제 → DB 영속화를 처리한다. 파티션 수가 곧 처리 병렬도다.
- **부하 평탄화(load leveling)**: 순간 10만 요청이 와도 Kafka가 버퍼가 되어 DB는 일정한 속도로 소비한다. 스파이크가 완만한 처리량으로 바뀐다.
- **멱등성**: `reservationId`를 키로 중복 소비를 방지한다(at-least-once 환경 가정).

## 6. 전략 ④ 부하 테스트 + 관측

- **k6**: 대기열 진입 → 폴링 → 예매까지의 시나리오를 가상 사용자(VU) 수천 명으로 재현한다(`infra/loadtest/`).
- **지표**: p95/p99 응답시간, 오버셀 발생 건수(0이어야 함), 대기열 처리량, Kafka consumer lag.
- **Grafana 대시보드**: 위 지표를 시각화해 "스파이크 전/후"를 한 화면에 담는다 → 포트폴리오 스크린샷으로 직접 활용.

## 7. 예매 시퀀스 (성공 경로)

```
User ─▶ Queue: 진입 요청
Queue ─▶ Redis: ZADD(now, userId)
User ◀─ Queue: 대기 토큰 + 내 순번
   ... 폴링 ...
Worker ─▶ Redis: ZPOPMIN → 입장 가능
User ◀─ Queue: 입장 토큰(JWT)
User ─▶ Reservation API: 좌석 점유 (입장 토큰 필요)
Reservation ─▶ Redis(Lua): 재고 차감 + hold(TTL)
User ─▶ Reservation API: 예매 확정
Reservation ─▶ Kafka: produce reservation.requested → 202
Consumer ─▶ DB: 재고 확정 + 주문 생성
Consumer ─▶ Payment: 결제 요청
Consumer ─▶ Redis: 결과 저장
User ◀─ (폴링/WS): 예매 완료
```

## 9. 의도적으로 단순화한 부분 (솔로 프로젝트 범위)

실제 결제 PG 연동은 mock으로 대체한다. 인증은 입장 토큰 검증 위주로 최소화한다. 멀티 리전·DR은 범위에서 제외한다. 이 선택들은 "트래픽 처리"라는 핵심에 집중하기 위한 의도적 스코프 컷이며, README에 명시해 면접에서 트레이드오프를 설명할 수 있게 한다.

## 10. MSA 구성 (back)

백엔드는 NestJS monorepo 모드로 **4개 마이크로서비스**로 분리한다. 분리 기준은 "독립적으로 스케일·배포·장애격리가 필요한가"이며, 티케팅의 세 트래픽 성격(폴링 폭주 / 쓰기 정합성 / 외부 결제)이 그대로 서비스 경계가 된다.

```
                ┌───────────┐
   Client ────▶ │  gateway  │  (REST 프록시/BFF, 입장토큰 검증)
                └─────┬─────┘
        ┌─────────────┼──────────────┐
        ▼ REST        ▼ REST         ▼ REST
 ┌────────────┐ ┌──────────────────┐ │
 │ queue-     │ │ reservation-     │ │
 │ service    │ │ service          │ │
 │ (대기열)    │ │ (예매·재고·event) │ │
 └─────┬──────┘ └────────┬─────────┘ │
       │ Redis           │ Kafka(pub) │
       ▼                 ▼            │
   [Redis]        [reservation.requested]
                         │
                         ▼ Kafka(sub)
                 ┌──────────────────┐
                 │ payment-service  │ (결제·확정)
                 └──────────────────┘
```

- **동기 통신**: gateway → 각 서비스 REST. (운영에선 K8s Ingress가 gateway 역할 일부 대체 가능)
- **비동기 통신**: reservation-service가 Kafka로 예매 이벤트 발행 → payment-service가 소비. 결제 장애가 예매 진입을 막지 않도록 격리.
- **공유 계약**: Kafka 이벤트/DTO는 `libs/contracts` 한 곳에 정의해 서비스 간 스키마 불일치를 방지.
- **스케일 전략**: 폴링이 집중되는 queue-service와 진입점 gateway를 우선 수평 확장(HPA). reservation은 쓰기 부하에 따라, payment는 consumer lag 기준으로 확장.
- **DB**: 정석은 DB-per-service. 솔로 단순화로 Postgres 1개 + 스키마 분리(catalog/orders)를 채택하고, 추후 분리 가능하도록 경계를 코드에서 유지.

### 왜 5개가 아니라 4개인가
event(카탈로그/재고 seed)는 읽기 중심이고 변경이 드물어, 초기엔 reservation-service에 흡수해 운영 부담을 줄였다. 트래픽이 커지거나 카탈로그 도메인이 복잡해지면 5번째 서비스로 분리한다 — 경계(EventController)를 이미 모듈로 격리해 두어 분리 비용이 낮다.
