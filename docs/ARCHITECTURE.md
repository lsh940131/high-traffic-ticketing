# 아키텍처

## 1. 설계 목표

이 프로젝트는 평소 트래픽은 낮지만 **티켓 오픈 순간에만 수만~수십만 명이 몰리는** 전형적인 스파이크 워크로드를 가정한다. 목표는 세 가지다. 첫째, 트래픽 스파이크에도 서비스가 죽지 않을 것(가용성). 둘째, 좌석/재고가 절대 초과 판매되지 않을 것(정합성). 셋째, 먼저 온 사용자가 먼저 처리될 것(공정성). 이 세 목표가 서로 충돌하는 지점에서 어떤 트레이드오프를 했는지가 이 프로젝트의 핵심 어필 포인트다.

## 3. 전략 ① 가상 대기열 (Waiting Queue)

트래픽이 백엔드를 직접 때리지 못하게 하는 **댐** 역할이다. 사용자가 예매 페이지에 진입하면 곧바로 비즈니스 로직을 타지 않고 대기열에 등록된다.

- **자료구조**: Redis Sorted Set. `score = 진입 타임스탬프(ms)`, `member = userId`. score 순서가 곧 입장 순서가 되어 FIFO 공정성을 보장한다.
- **순번 조회**: `ZRANK`로 내 앞에 몇 명이 있는지 O(log N)에 계산한다. 프론트는 이 값을 폴링하여 "내 순번 / 예상 대기시간"을 보여준다.
- **입장 제어**: 별도 워커가 일정 주기로 `ZPOPMIN`을 통해 "활성 사용자 풀(active set)"이 정원에 찰 때까지 사용자를 꺼내, 짧은 만료의 **입장 토큰(JWT)**을 발급한다. 이 토큰이 있어야 예매 API를 호출할 수 있다.
- **효과**: 백엔드는 항상 "정원만큼"의 사용자만 상대하므로 부하가 일정하게 유지된다.
- **읽기 vs 쓰기 경계**: 대기열은 **쓰기 경합**(좌석 점유·예매·결제) 게이트일 뿐, 상세 페이지의 잔여석 등 **읽기**는 대기열 앞단이다. 잔여 카운트는 Redis 캐시(수초 TTL)+레플리카로 서빙하고 표시는 advisory(근사치) — 진실의 원천은 점유 순간의 Lua 연산. 플로우: `상세(자유 조회) → 예매하기 → [대기열] → 좌석선택(점유)`.

### 3.1 순번 · 예상 대기시간 산출 (대기중 UI)

- **순번**: `ZRANK(queue, userId)`로 내 앞 인원을 O(log N)에 조회. 프론트가 2~3초 폴링(`GET /queue/status`)으로 받아 "내 앞에 N명" 표시. 읽기라 캐시·레플리카로 흡수.
- **예상 대기시간**: `ETA(초) = 내_순번 / 입장속도(초당 입장 인원)`.
  - 입장속도 = (a) 정적 `정원 / 평균 체류시간`, 또는 (b) 동적 — 워커의 실제 `ZPOPMIN` 비율을 최근 N초 이동평균(EWMA)으로 측정(권장, 실처리율 반영).
  - 표시는 구간화·반올림 + smoothing해서 숫자 튐 방지. ETA는 추정치(advisory)라 입장속도 변화에 따라 변동.
- **통신**: 폴링으로 충분(단방향·저빈도 갱신). 대규모 동시 대기에선 영속 소켓(WS)보다 짧은 요청이 캐시·레플리카로 더 단순하게 확장됨. WS/SSE는 향후 선택지로만 둔다.

### 3.2 입장 유예시간 · 슬롯 회수 (입장가능 UI)

- 워커가 `ZPOPMIN`으로 사용자를 꺼내 active set에 넣을 때 **이중**으로 유예시간을 건다:
  - **입장 토큰(JWT)** 발급, `exp = now + 유예시간`(예: 3분). 예매 API는 이 토큰의 서명·exp 검증을 통과해야 호출 가능(게이트웨이).
  - Redis 슬롯 키 `SET admit:{userId} EX 180` — 정원 한 칸을 차지하는 "자리 예약".
- 프론트 카운트다운 = 토큰 `exp`까지 남은 시간(서버 시각 기준).
- **미입장 시 자동 회수**: 시간 내 입장(토큰 들고 좌석선택 진입)하지 않으면 `admit` 키 TTL 만료 → 슬롯 반환 → 정원이 비면 워커가 다음 사용자 `ZPOPMIN`. 만료된 사용자는 토큰 무효 → 현재 시각 score로 대기열 맨 뒤 재등록(재대기).
- **목적**: 입장만 시키고 안 들어오는 유령이 정원을 막지 않게 TTL로 강제 비워 처리량을 일정하게 유지.

## 4. 전략 ② 재고 동시성 제어

대기열을 통과해도, 인기 좌석에는 여전히 동시 요청이 몰린다. 여기서 오버셀을 막는 것이 핵심이다.

- **DB 락만으로는 부족**: 행 잠금/비관적 락은 스파이크에서 커넥션 풀을 고갈시키고 데드락 위험이 크다. 그래서 **1차 방어선은 Redis**다.
- **Redis Lua 원자 연산**: 좌석 점유 차감을 Lua 스크립트로 처리한다. "남은 재고 확인 → 0보다 크면 차감 → 점유 키 설정"을 단일 원자 연산으로 실행해 경합 구간(check-then-act race)을 제거한다.
- **좌석 점유 TTL**: 좌석을 고른 사용자에게 N분짜리 임시 점유(hold)를 준다. 결제까지 못 가면 자동 만료되어 재고로 복귀한다.
- **2차 방어선 DB**: 최종 확정 시 `ticket.status`를 **조건부 UPDATE**한다(`WHERE status = 'HELD'`). 경합한 요청 중 단 1건만 1행을 갱신하고 나머지는 0행 → 주문이 FAILED로 우아하게 실패한다. Redis는 빠른 게이트, DB는 진실의 원천(source of truth).
  - **유니크 제약을 쓰지 않은 이유**: Reservation 행은 취소·재판매를 위해 같은 좌석에 여러 번 생길 수 있어야 한다. 그래서 유니크로 막는 대신 **좌석 상태 전이 자체를 원자적으로** 만들었다. 오버셀 판정도 Reservation 수가 아니라 `SOLD` 티켓 수로 한다.

## 5. 전략 ③ 비동기 예매/결제 (Kafka)

예매 "요청"과 예매 "확정"을 분리한다.

- **Producer**: 예매 API는 검증만 마치면 즉시 202(Accepted)를 반환한다. 사용자 응답 시간이 결제·DB I/O에 묶이지 않는다.
- **트랜잭셔널 아웃박스**: API가 Kafka로 직접 발행하지 않는다. 예매 트랜잭션이 DB에 `Outbox` 행을 **함께 커밋**하고, 별도 릴레이가 PENDING을 폴링해 `reservation.requested`로 발행 후 SENT로 표시한다. "DB 커밋"과 "이벤트 발행"은 하나의 원자 단위로 묶을 수 없으므로(dual-write), 직접 발행하면 커밋 후 발행 실패 시 **유실**되거나 발행 후 롤백 시 **유령 이벤트**가 생긴다.
- **Consumer**: 컨슈머 그룹이 자기 속도대로 이벤트를 소비하며 재고 확정 → 결제 → DB 영속화를 처리한다. 파티션 수가 곧 처리 병렬도다.
- **부하 평탄화(load leveling)**: 순간 10만 요청이 와도 Kafka가 버퍼가 되어 DB는 일정한 속도로 소비한다. 스파이크가 완만한 처리량으로 바뀐다.
- **멱등성**: 컨슈머가 `processed:order:{orderId}` 마커를 Redis `SET NX`로 걸어 중복 소비를 방지한다(at-least-once 환경 가정).

## 6. 전략 ④ 부하 테스트 + 관측

- **k6**: 대기열 진입 → 폴링 → 예매까지의 시나리오를 가상 사용자(VU) 수천 명으로 재현한다(`infra/loadtest/`). 스크립트 3종이 각각 "죽지 않는가 / 오버셀 0인가 / replica↑면 처리량↑인가"에 답한다.
- **지표**: p95/p99 응답시간, 오버셀 발생 건수(0이어야 함), 대기열 처리량, 서비스별·**파드별** CPU.
- **Grafana 대시보드**: k6 지표(remote-write)와 서버 지표를 한 화면에 놓아 "부하 → 포화 → 파드 증설 → 처리량 회복"을 이어서 본다.
- **부하생성기 천장을 먼저 잰다**: 부하를 만드는 쪽이 먼저 한계에 닿으면 서버에 여유가 있어도 곡선이 눕는다. 이걸 확인하지 않으면 측정 자체가 무의미해진다.
- **결과**: [`../infra/loadtest/RESULTS.md`](../infra/loadtest/RESULTS.md)가 정본. 오버셀 0 · 수평 확장 3.76배 · 단일 노드 천장 ≈ 1,800 rps, 그리고 부하 테스트가 잡아낸 버그 2건.

## 7. 예매 시퀀스 (성공 경로)

```
User ─▶ Queue: 진입 요청
Queue ─▶ Redis: ZADD(now, userId)
User ◀─ Queue: 대기 토큰 + 내 순번
   ... 폴링 ...
Worker ─▶ Redis: ZPOPMIN → 입장 가능
User ◀─ Queue: 입장 토큰(JWT)
User ─▶ Reservation API: 좌석 점유(hold) (입장 토큰 필요)
Reservation ─▶ Redis(Lua): 점유 차감 + HELD(TTL)     ── 좌석=HELD, 주문=PENDING_PAYMENT
User ─▶ Reservation API: 결제 진행 요청
Reservation ─▶ Kafka: produce reservation.requested → 202   ── 주문=PROCESSING
Consumer ─▶ Payment: 결제 (성공해야 다음 단계로)
Consumer ─▶ Redis/DB: 좌석 SOLD + 주문 CONFIRMED      ── 결제 성공 후에만 확정
User ◀─ (주문 상태 폴링): 예매 완료
```

## 7.1 좌석/주문 상태 머신 (결제 실패 처리 포함)

확정(SOLD)은 **결제 성공 후에만** 일어난다. 처리중에 미리 확정하지 않는다.

```
좌석:  AVAILABLE ─점유→ HELD(TTL N분) ─결제성공→ SOLD
                          └─(TTL 만료 / 사용자 취소)→ AVAILABLE
주문:  PENDING_PAYMENT → PROCESSING → CONFIRMED
                                   ├→ PAYMENT_FAILED  (좌석은 HELD 유지)
                                   └→ EXPIRED         (TTL 만료 시에만 좌석 release)
```

- **결제 실패 ≠ 좌석 즉시 release.** 사용자에게 이미 "N분 안에 결제" 점유 타이머를 약속했으므로 그 타이머가 공정한 경계다. 실패 시 같은 좌석을 HELD로 유지한 채 재시도/다른 결제수단을 제공한다.
- 좌석 release는 오직 (a) 점유 TTL 만료, (b) 사용자의 명시적 취소. 시스템이 결제 실패를 이유로 좌석을 회수하지 않는다(bad UX 회피).
- `payment-service` 컨슈머는 이 모델대로 동작한다: 결제 먼저 → 성공 시에만 좌석 SOLD, 실패 시 주문만 FAILED로 두고 좌석은 건드리지 않음.

`pc`를 따로 둔 이유는 코어 수다. 노트북 4코어에선 파드를 늘려도 같은 CPU를 나눠 쓸 뿐이라 수평 확장 곡선이 안 나온다. 12스레드 PC로 클러스터를 옮기고 **노트북을 부하생성기로 뒤집어** 측정을 물리적으로 분리했다.

## 9. 의도적으로 단순화한 부분 (솔로 프로젝트 범위)

실제 결제 PG 연동은 mock으로 대체한다. 멀티 리전·DR은 범위에서 제외한다. 인증은 초기엔 입장 토큰 검증만 두려 했으나, 전체 플로우를 시연하려면 로그인이 필요해 `user-service`(AT/RT 회전)까지 구현했다. 이 선택들은 "트래픽 처리"라는 핵심에 집중하기 위한 의도적 스코프 컷이며, README에 명시해 면접에서 트레이드오프를 설명할 수 있게 한다.

## 10. MSA 구성 (back)

백엔드는 NestJS monorepo 모드로 **5개 마이크로서비스**로 분리한다. 분리 기준은 "독립적으로 스케일·배포·장애격리가 필요한가"이며, 티케팅의 트래픽 성격(로그인 스탬피드 / 폴링 폭주 / 쓰기 정합성 / 외부 결제)이 그대로 서비스 경계가 된다.

```
                        ┌───────────┐
   Client ─────────────▶│  gateway  │  (REST 프록시/BFF, 토큰 검증)
                        └─────┬─────┘
   ┌──────────────┬───────────┼──────────────┐
   ▼ REST         ▼ REST      ▼ REST         ▼ REST
┌──────────┐ ┌────────────┐ ┌──────────────────┐ │
│ user-    │ │ queue-     │ │ reservation-     │ │
│ service  │ │ service    │ │ service          │ │
│ (인증)    │ │ (대기열)    │ │ (예매·재고·카탈로그)│ │
└──────────┘ └─────┬──────┘ └────────┬─────────┘ │
       │ Redis           │ Kafka(pub) │
       ▼                 ▼            │
   [Redis]        [reservation.requested]
                         │
                         ▼ Kafka(sub)
                 ┌──────────────────┐
                 │ payment-service  │ (결제·확정)
                 └──────────────────┘
```

- **동기 통신**: gateway → 각 서비스 REST. (운영에선 K8s Ingress가 gateway 역할 일부 대체 가능)
- **비동기 통신**: reservation-service가 Kafka로 예매 이벤트 발행 → payment-service가 소비. 결제 장애가 예매 진입을 막지 않도록 격리.
- **공유 계약**: Kafka 이벤트/DTO는 `libs/contracts` 한 곳에 정의해 서비스 간 스키마 불일치를 방지.
- **스케일 전략**: 폴링이 집중되는 queue-service와 진입점 gateway를 우선 수평 확장(HPA). reservation은 쓰기 부하에 따라, payment는 consumer lag 기준으로 확장.
  - 실측으로 이 예측이 맞았다. 대기열 워크로드의 병목은 **queue-service**였고(파드당 1코어에 정확히 붙음), gateway는 6파드에서도 59%였다. 1→6 replica에서 처리량 3.76배.
  - 다만 **L4 로드밸런싱 + HTTP keep-alive** 때문에 스케일아웃한 파드가 트래픽을 못 받는 함정이 있었다. k8s Service는 커넥션을 맺는 순간에만 파드를 고르므로, 커넥션이 재사용되면 새 파드는 논다. gateway의 커넥션 풀에 수명을 줘 해결했다(정석은 L7 로드밸런싱).
- **DB**: 정석은 DB-per-service. 솔로 단순화로 **Postgres 1개를 공유**하고 스키마도 나누지 않았다. 서비스 경계는 코드(모듈·계약)로만 지키며, 분리 시점의 마이그레이션 비용을 감수하는 대신 지금의 운영 복잡도를 줄인 선택이다.

### 카탈로그를 왜 별도 서비스로 두지 않았나
공연 카탈로그(목록·상세·좌석맵)는 읽기 중심이고 변경이 드물어, reservation-service의 `concert` 모듈로 흡수해 운영 부담을 줄였다. 트래픽이 커지거나 도메인이 복잡해지면 분리한다 — 경계를 이미 모듈로 격리해 두어 비용이 낮다.
