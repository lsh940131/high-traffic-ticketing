# 부하 테스트 결과

티켓 오픈 스파이크를 재현해 **① 시스템이 죽지 않는가 ② 오버셀이 0인가
③ 파드를 늘리면 처리량이 늘어나는가**를 수치로 검증한다.
스크립트는 이 디렉터리의 `waiting-queue.js`(대기열)·`reservation.js`(예매/오버셀)·
`scale-out.js`(수평 확장), 공용 헬퍼 `common.js`.

측정 환경이 둘이다. ①②는 **환경 A(노트북 4코어)**, ③은 코어가 모자라 못 했던 것을
**환경 B(PC 12스레드)**로 옮겨 수행했다. 토폴로지가 서로 반대인 점에 주의.

---

## 환경 A — 노트북 k3s (4코어) · 시나리오 ①②

```
[Windows PC 192.168.219.103]              [Linux 노트북 192.168.219.150]
  k6 v2.1.0 (부하 생성)  ──── LAN ────►     k3s 단일 노드 (4코어) · gateway NodePort :30300
  (부하 대상과 물리 분리 = 측정 오염 없음)     전체 스택(gateway·queue·reservation·payment·user
                                            + redis·postgres·kafka·minio)
```

- **대상 진입점**: `http://192.168.219.150:30300` (gateway, 단일 진입점 BFF).
- **인증 모델 — 사전 인증(pre-authenticated)**: k6가 `JWT_SECRET`으로 AT를 직접 서명 발급해
  "이미 로그인된 사용자"를 시뮬레이션한다. 실제 티켓팅과 동일(오픈 전 로그인, 오픈 순간엔 대기열·예매만).
  - 이유: 초기 3,000 스파이크에서 **실 로그인을 포함했더니 bcrypt(user-service)가 CPU 포화**되어
    대기열 측정을 오염시켰다. 로그인 경로 자체는 register/login 200으로 별도 검증됨.
- **시드 데이터**: 공연 10개(각 스탠딩 1,000장), 부하 유저 5,000명(`load-<i>@ticketing.dev`).
- **측정 도구**: k6 요약(p95/실패율/RPS) + `kubectl top`(서버측 CPU/메모리) + postgres 직접 쿼리(오버셀).

## 시나리오 ① 대기열 스파이크 (`waiting-queue.js`)

`ramping-vus`로 20s간 0→PEAK 급증 후 유지. 각 VU: 대기열 `enter` → `status` 폴링.

| PEAK VU | `enter` p95 | `enter` 실패율 | 판정 |
|--------:|------------:|---------------:|------|
| 10 (기준선) | **55 ms** | 0% | 여유 |
| 1,000 | 7.5 s | 16.7% | 저하 시작 |
| 3,000 | 60 s (타임아웃) | 39% | 포화 |

**피크 시 서버측(`kubectl top`, PEAK=3000):**

| 파드 | CPU | 해석 |
|------|----:|------|
| gateway ×2 | ~900m (한계 1 core 근접) | **프록시가 먼저 포화 = 병목** |
| queue-service ×2 | ~600m (여유) | **대기열 로직은 한가함** |
| user-service | 유휴 | 사전 인증이라 로그인 부하 없음 |
| **노드 전체** | **CPU 81% / 메모리 53%** | CPU가 벽, 메모리는 여유 |

> **핵심**: 부하는 gateway 프록시·노드 CPU에 걸리고 **가상 대기열(queue-service)은 여유** —
> 즉 대기열이 설계대로 뒷단을 보호한다. 단일 4코어 노드라 수천 동시성에서 프록시 계층이 먼저 포화.

## 시나리오 ② 오버셀 0 (`reservation.js`)

`constant-arrival-rate`(초당 N명 도착)로 한정 스탠딩 재고(1,000)에 예매를 몰아붙인다.
흐름: 사전 AT → 대기열 `enter`(입장 토큰) → `hold`(스탠딩 원자 선점) → `reserve`(주문).

### 🔍 부하테스트가 발견한 버그 → 수정

- **증상**: 고동시성에서 재고가 남아도 대부분 "매진/혼잡"(409)으로 거절, 판매 극소수.
- **원인**: `holdStanding`이 AVAILABLE 티켓 **첫 31개(`take: qty+30`)만** 조회. hold은 Redis에만
  기록(티켓 `status`는 AVAILABLE 유지) → 매 조회가 **같은 31개**를 반환 → 그 31개가 hold되면
  이후 전원 "매진". **동시 스탠딩 선점이 ~31에서 천장.** (저동시성 스모크에선 안 드러남)
- **수정**(`booking.service.ts` `holdStanding`): 후보창 확대(`max(qty*50, 300)`) + 무작위 구간(skip)
  + Fisher-Yates 셔플 → 동시 구매자가 서로 다른 좌석 선택. 스탠딩은 fungible이라 무작위 안전.
- **효과**: Redis 동시 hold **21 → 934** 로 개선.

### ✅ 오버셀 검증 (권위 지표 = `ticket.status`)

> 오버셀 방어는 **2층**: ① Redis Lua 원자 hold(동일 좌석 동시 점유 차단) ②
> 결제 시 `ticket.status` **원자적 조건부 UPDATE**(단 1건만 SOLD). Reservation 행은 취소·재판매를
> 위해 유니크를 두지 않으므로(경합 시 PENDING 중복 가능), **오버셀은 `SOLD` 수로 판정**한다.

| 테스트 | 조건 | SOLD | CONFIRMED | FAILED(경합 패자) | **이중 CONFIRMED** |
|--------|------|-----:|----------:|-----------------:|:------------------:|
| ⓐ 대기열 게이팅 | 정원 1,000 · 40/s | 392 | 392 | 110 | **0** |
| ⓑ 직접 경합 | 정원 5,000(게이팅 X) · 60/s | 296 | 296 | 70 | **0** |

- **오버셀 0** — 어떤 티켓도 2개 이상의 CONFIRMED 주문에 팔리지 않음. 재고(1,000) 초과 없음.
- **FAILED 주문 = 2차 방어선 작동 증거**: 같은 좌석을 경합한 패자는 결제 시 `status` UPDATE가 0행
  → 주문 FAILED로 **우아하게 실패**(크래시·오버셀 없음).
- ⓑ는 **대기열 보호를 제거**하고 재고에 직접 몰아도 오버셀 0 → **재고 방어선 자체가 정합성을 보장**함을 증명.
- (SOLD가 재고보다 적은 것은 노드 CPU 포화·hold 혼잡으로 인한 완결률 저하 때문이며, 안전성 증명과 무관.)

## 환경 B — PC k3d (12스레드) · 시나리오 ③

노트북 4코어에선 파드를 늘려도 같은 CPU를 나눠 쓸 뿐이라 수평 확장 곡선이 안 나왔다.
**토폴로지를 뒤집어** 자원이 넉넉한 PC를 클러스터로, 노트북을 부하생성기로 삼았다.

```
[Linux 노트북 192.168.219.150]            [Windows PC 192.168.219.103]
  k6 v2.1.0 (부하 생성, 4코어)  ─ LAN ─►    k3d(k3s) 단일 노드 · 12스레드 / 15GB
  (k3s는 내려서 CPU 확보)                    gateway NodePort :30300
                                            + prometheus·grafana (파드 단위 스크레이프)
```

- **k3d 선택 이유**: 노트북과 동일한 k3s라 매니페스트 그대로 재사용 + metrics-server 내장(HPA 전제).
  빌드도 클러스터도 같은 PC라 레지스트리 없이 `k3d image import`. (`infra/k8s/README-pc.md`)
- **스케일 대상 requests 500m**(base 200m 대비 상향). HPA 목표 70% = 파드당 350m — 200m 기준이면
  70%가 140m라 부하 즉시 max까지 튀어 증식 계단이 안 보인다.
- **네트워크**: TCP RTT p50 9.6ms / 지터 ~2ms. 모든 요청에 상수로 얹히지만 replica 수와
  무관하므로 **지연 변화량 측정은 왜곡되지 않는다.**

### 부하생성기 천장 먼저 (측정 유효성)

부하를 만드는 쪽이 먼저 한계에 닿으면 서버에 여유가 있어도 곡선이 눕는다. 본 측정 전에 확인:

| | 값 | 판정 |
|---|---|---|
| 지속 처리량 | 1,698 req/s (VU 336에서 이미 포화, 1,200까지 올려도 동일) | |
| **k6 프로세스 CPU** | **128% / 400%** | 노트북은 **천장이 아님** (여유 3배) |
| queue-service CPU | 3.94 / 4코어 | **여기가 천장** |

→ 이 워크로드의 병목은 **queue-service**다. gateway는 6파드에서도 59%였다.
문서 계획엔 "gateway를 늘린다"고 적혀 있었으나, **병목이 아닌 걸 늘리면 곡선이 안 움직인다** →
측정 대상을 queue-service로 교체.

### 🔍 부하테스트가 발견한 버그 → 수정 (2)

- **증상**: queue-service를 3→4→6으로 늘려도 처리량이 1,4xx에서 멈춤. 노드는 52%, gateway도 여유,
  k6도 여유. 그런데 **파드 6개 중 3개만 CPU 1.0을 태우고 나머지 3개는 0.005**. Endpoints엔 6개 다 정상.
- **원인**: **k8s Service(L4) + HTTP keep-alive의 조합.** kube-proxy는 **TCP 커넥션을 맺는 순간
  한 번** 백엔드 파드를 고르고, 그 커넥션의 모든 요청은 끝까지 같은 파드로 간다. Node 19+는
  `http.globalAgent`가 기본 `keepAlive: true`라 `@nestjs/axios`를 무설정으로 쓰면 자동으로 이 상태가 된다.
  → **스케일아웃해도 새 파드는 영원히 논다.** 기본 스케줄링 `'lifo'`(최근 쓴 소켓 우선 재사용)가
  쏠림을 한 번 더 키운다.
- **증거(자연 실험)**: 부하를 잠깐 끊어 유휴 소켓이 정리되게 하자, 재개 시 커넥션이 6개 엔드포인트
  전체로 새로 맺히며 **동일 파드 수에서 1,461 → 2,055 rps (+41%)**, 파드별 CPU도 3/6 편중에서
  `0.88 0.87 0.87 0.87 0.86 0.86`으로 균등화. **바뀐 변수는 커넥션 재수립뿐.**
- **수정**(`upstream.service.ts`): 커넥션 풀에 수명을 부여. 30초마다 새 `http.Agent`로 교체하고
  옛 에이전트는 10초 유예 뒤 정리(`destroy()`를 즉시 부르면 **사용 중 소켓까지 끊어** 진행 중 요청이
  실패한다). `scheduling: 'fifo'`로 풀 전체를 돌려 써 백엔드에도 고르게 분산. `UPSTREAM_AGENT_TTL_MS`로 조절.
- **트레이드오프**: 재분배까지 최대 TTL만큼 지연. **정석은 L7 로드밸런싱**(서비스 메시·Envoy)으로
  요청 단위 분배를 하는 것이고, 이 수정은 의존성 없이 같은 문제를 덮는 실용적 대안이다.
  gRPC/HTTP2였다면 단일 멀티플렉스 커넥션이라 문제가 더 심각해 L7이 사실상 필수다.

### 수평 확장 곡선 (`scale-out.js`, VU 400 고정)

`constant-vus` + think time 없음 → `처리량 = VU / 지연`. 파드를 늘려 지연이 떨어지면 그만큼 RPS가 오른다.
단계마다 k6를 90초씩 독립 실행하고 **각 런의 자체 요약**을 채택(remote-write 경유 지표는 과소보고됨).
실패 요청은 503을 빨리 뱉어 RPS를 부풀리므로 **성공 처리량**으로 비교한다.

| queue replica | 성공 처리량 | p95 (요청) | p95 (왕복) | 실패율 | queue CPU | 활성 파드 |
|--------------:|-----------:|----------:|----------:|-------:|----------:|:---------:|
| 1 | **494 req/s** | 6.38 s | 8.64 s | 6.89% | 1.00 / 1 | 1/1 |
| 2 | **930** | 592 ms | 956 ms | 29.79% | 1.99 / 2 | 2/2 |
| 3 | **1,322** | 443 ms | 738 ms | 0.32% | 2.98 / 3 | 3/3 |
| 4 | **1,471** | 435 ms | 704 ms | 0.00% | 3.69 / 4 | 4/4 |
| 6 | **1,858** | 351 ms | 607 ms | 0.00% | 5.19 / 6 | 6/6 |

- **1→6 replica: 처리량 3.76배, 왕복 p95 8.64s → 607ms (14배 개선).** 수정 후에는 모든 단계에서
  파드가 전부 일한다(`4/4`, `6/6`).
- 파드당 효율은 494 → 465 → 441 → 368 → 310으로 체감 — 노드 CPU와 gateway 경합이 커지기 때문.

### 단일 노드 천장

| | RPS | p95 | 노드 CPU |
|---|---:|---:|---:|
| queue = 6 | **1,820** | 374 ms | 9,663m (80%) |
| queue = 8 | **1,750** | 386 ms | 10,226m (85%) |

**곡선은 6에서 끝난다.** 8번째 파드는 처리량을 못 늘리고 노드만 더 먹는다(-4%).
12스레드 단일 노드의 천장 ≈ **1,800~1,850 req/s**. (queue=6 재측정 1,820은 위 표 1,858을 오차 2%로 재현)

### HPA 자동 증식 / 축소

`infra/k8s/hpa` 애드온(gateway·queue 2~8, reservation 1~6, 목표 CPU 70%) 적용 후 VU 400을 5분.

```
t=  0s   gateway 2p /  0%    queue 2p /  0%     ← min 대기
t= 40s   gateway 2p /119%    queue 2p / 97%     ← 목표 초과 감지
t= 60s   gateway 5p /124%    queue 5p /199%     ← 20초 만에 2→5
t=100s   gateway 6p / 80%    queue 8p /122%     ← queue는 max 도달
t=120s   gateway 6p / 66%    queue 8p /102%     ← gateway 균형점 안착
t=305s   [부하 종료]
t=400s   gateway 5p          queue 7p           ← 축소 시작 (종료 후 ~95초)
t=480s   gateway 2p          queue 4p           ← 30초당 1파드
```

- **gateway가 6파드 / 67%에서 스스로 균형점을 찾았다** — 목표 70% 바로 아래.
- 증식은 즉시, 축소는 60초 안정화 후 30초당 1파드 — `behavior`에 넣은 **비대칭이 의도대로** 동작.
  기본값(축소 안정화 300초)이면 시연 시간 내에 축소를 관찰할 수 없다.
- **HPA의 한계가 드러난 지점**: queue-service를 max=8까지 밀어붙였지만, 위 천장 측정대로 6개 이후로는
  처리량이 안 는다. HPA는 **파드당 CPU 사용률**만 보므로 "늘려도 처리량이 안 늘어난다"를 알 방법이 없다.
  사용률 기반 오토스케일링은 노드 천장을 감지하지 못한다.

### 남은 의문 (미검증)

queue=2에서 실패율이 **29.79%**로, queue=1(6.89%)보다 높게 튄다(단조적이지 않음).
가설은 **재시도 증폭** — gateway가 `TIMEOUT_MS=2000` + 재시도 2회 구조라, 지연이 2초 경계에 걸치는
구간에서 타임아웃 → 재시도 → 부하 3배 → 더 많은 타임아웃의 악순환이 생길 수 있다. 파드 1개일 땐
지연이 경계를 한참 넘어 서킷이 열린 채 빠르게 흘려보내고, 3개 이상이면 안전하게 2초 아래라 조용하다.
확인하려면 재시도를 끄고 같은 지점을 재측정해야 한다.

## 결론

1. **오버셀 0 — 증명됨** (대기열 게이팅 유무와 무관). 정합성은 코어 수가 아닌 원자적 방어의 문제라 하드웨어 독립적.
2. **가상 대기열이 뒷단을 보호** — 대기열 로직은 저비용(여유), 부하는 진입/프록시 계층에 걸림.
3. **수평 확장 증명됨** — queue-service 1→6 replica에서 **처리량 3.76배(494 → 1,858 rps),
   왕복 p95 14배 개선**. HPA 자동 증식·축소까지 라이브 관찰.
4. **부하테스트가 실제 버그를 두 번 발견·수정·재검증**
   — ① `holdStanding` 후보창 붕괴(동시 hold 21 → 934)
   — ② **L4 Service + keep-alive로 인한 스케일아웃 무효화**(동일 파드 수에서 +41%)
5. **양대 오버셀 방어선 모두 검증** — Lua 원자 hold(1차) + `ticket.status` 원자 UPDATE(2차).

### 한계 (의도된 스코프)
